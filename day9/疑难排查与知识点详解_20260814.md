# STM32 OTA 分区跳转 — 疑难排查与知识点详解

> 日期：2026-08-14
> 项目：STM32F407ZE 风扇控制（Bootloader + A/B 双区 APP）
> 涉及目录：`day9/Bootloader_stm`、`day9/A_BLE_bt_wifi_key_hc04_temp_pwm_8_14_am`、`day9/B_BLE_bt_wifi_key_hc04_temp_pwm_8_14 _am`

## 总览

今天共遇到 **4 个疑难**，按解决顺序排列：

| # | 疑难 | 现象 | 根因 | 解决方案 |
|---|------|------|------|---------|
| 1 | Bootloader 拒绝跳转复杂 APP | 简单 LED 项目能跳，复杂 APP 总进 else 死循环 | 有效性检查只认 SRAM1，复杂 APP 栈顶在 SRAM2 | 扩展 SRAM2 检查 + Reset_Handler 范围 + Thumb 位 |
| 2 | A/B 区大小不一 | 想让 A=B 等大 | 原分区 A<B | Flash 三等分：Bootloader 256KB + A 384KB + B 384KB |
| 3 | A↔B 互跳卡死/花屏 | Bootloader→A/B 正常，A↔B 互跳 OLED 花屏卡死 | APP 间直接跳转外设残留（软件 IIC 死锁等） | 软复位法：RTC 备份寄存器传标志 + NVIC_SystemReset |
| 4 | 编译报 missing closing quote | 编辑后编译报引号未闭合 + 级联错误 | 文件被存成 UTF-8，Keil 按 GBK 读取中文乱码 | 将 .c 文件转回 GBK 编码 |

## 疑难一：Bootloader 拒绝跳转复杂 APP

### 1.1 现象

- 烧录简单的 LED 闪烁项目到 A 区，Bootloader 能正常跳转运行。
- 烧录复杂的蓝牙/WiFi/FreeRTOS 项目到 A 区，Bootloader **总是进入 else 死循环分支**（错误指示灯闪），无法跳转。

### 1.2 根因

Bootloader 的 `Check_APP_Valid()` 函数只检查栈顶地址（SP）是否在 **SRAM1** 范围内：

```c
// 错误写法：只检查 SRAM1
if ((sp >= 0x20000000) && (sp < 0x20020000)) {
    sp_valid = 1;
}
```

但复杂 APP（带 FreeRTOS + 大量外设）链接时把主栈放在了 **SRAM2**（`0x10000000` 区域），导致 SP 落在 SRAM2，被误判为"无效 APP"。

### 1.3 解决方案

扩展有效性检查，覆盖 STM32F407ZE 的两个 SRAM 区域，并增加 Reset_Handler 地址和 Thumb 位校验：

```c
uint8_t Check_APP_Valid(uint32_t app_addr)
{
    volatile uint32_t *pAddr = (volatile uint32_t *)app_addr;
    uint32_t sp = pAddr[0];            // 第一个字 = 栈顶地址
    uint32_t reset_handler = pAddr[1]; // 第二个字 = Reset_Handler 地址

    int sp_valid = 0;
    // SRAM1: 0x20000000 - 0x2001FFFF (128KB)
    if ((sp >= 0x20000000) && (sp < 0x20020000)) sp_valid = 1;
    // SRAM2: 0x10000000 - 0x10000FFFF (64KB)
    else if ((sp >= 0x10000000) && (sp < 0x10010000)) sp_valid = 1;

    if (sp_valid) {
        // Reset_Handler 必须在 A/B 区 Flash 范围内
        if ((reset_handler >= 0x08040000) && (reset_handler < 0x08100000)) {
            if (reset_handler & 1) return 1;  // Thumb 位检查
        }
    }
    return 0;
}
```

### 1.4 涉及知识点

#### ① APP 起始处的向量表结构

APP 烧录到 Flash 后，起始地址处存放的是**异常向量表**，前两个字段最关键：

| 偏移 | 内容 | 含义 |
|------|------|------|
| 0x00 | 栈顶地址 (SP) | 主栈指针初始值，指向 SRAM 某地址 |
| 0x04 | Reset_Handler | 复位中断服务程序入口地址 |
| 0x08 | NMI_Handler | 不可屏蔽中断入口 |
| 0x0C | HardFault_Handler | 硬件错误中断入口 |
| ... | ... | 其他异常/中断 |

Bootloader 判断 APP 是否有效，就是读这两个字：SP 必须指向合法 SRAM，Reset_Handler 必须指向合法 Flash。

#### ② STM32F407ZE 的两块 SRAM

| 区域 | 起始地址 | 结束地址 | 大小 | 用途 |
|------|----------|----------|------|------|
| SRAM1 | 0x20000000 | 0x2001FFFF | 128KB | 通用主内存 |
| SRAM2 | 0x10000000 | 0x1000FFFF | 64KB | 高速 CCN RAM，可做栈/堆 |

简单项目栈顶默认在 SRAM1，复杂项目（FreeRTOS 任务多、堆栈大）链接器可能把主栈分配到 SRAM2。**有效性检查必须两个区都认**。

#### ③ Thumb 指令集位

ARM Cortex-M 内核只支持 Thumb-2 指令集。所有函数地址（包括 Reset_Handler）的**最低位必须为 1**，这个 1 不是地址的一部分，而是"这是 Thumb 指令"的标志位。跳转时硬件会自动忽略该位并切换到 Thumb 模式。检查 `reset_handler & 1` 可确认它是合法的函数入口。

## 疑难二：Flash 分区三等分

### 2.1 现象

原方案 A 区小、B 区大，不满足"A/B 应一样大"的 OTA 双备份要求。

### 2.2 解决方案

STM32F407ZE 共 **1MB Flash**，按扇区边界三等分：

```
┌──────────────────────────────────────────────────────────┐
│ Bootloader  扇区 0-5   0x08000000 - 0x0803FFFF  256KB    │
├──────────────────────────────────────────────────────────┤
│ A 区 APP    扇区 6-8   0x08040000 - 0x0809FFFF  384KB    │
├──────────────────────────────────────────────────────────┤
│ B 区 APP    扇区 9-11  0x080A0000 - 0x080FFFFF  384KB    │
└──────────────────────────────────────────────────────────┘
```

### 2.3 需要同步修改的配置（每个 APP 项目 3 处）

| 配置项 | A 区 | B 区 | 作用 |
|--------|------|------|------|
| IROM1 Start | 0x08040000 | 0x080A0000 | 告诉链接器代码放在哪 |
| IROM1 Size | 0x60000 (384KB) | 0x60000 (384KB) | 代码区最大范围 |
| VECT_TAB_OFFSET | 0x00040000 | 0x000A0000 | 中断向量表偏移 |
| FlashDriverDll FS/FL | 与 IROM 一致 | 与 IROM 一致 | 告诉烧录器烧到哪 |

### 2.4 涉及知识点

#### ① STM32F407ZE Flash 扇区结构

F407 的 1MB Flash 分 12 个扇区，**大小不均匀**：

| 扇区 | 起始地址 | 大小 |
|------|----------|------|
| 0 | 0x08000000 | 16KB |
| 1 | 0x08004000 | 16KB |
| 2 | 0x08008000 | 16KB |
| 3 | 0x0800C000 | 16KB |
| 4 | 0x08010000 | 64KB |
| 5 | 0x08020000 | 128KB |
| 6 | 0x08040000 | 128KB |
| 7 | 0x08060000 | 128KB |
| 8 | 0x08080000 | 128KB |
| 9 | 0x080A0000 | 128KB |
| 10 | 0x080C0000 | 128KB |
| 11 | 0x080E0000 | 128KB |

**关键约束**：Flash 擦除以扇区为单位，分区边界必须落在扇区边界上，否则擦除一个分区会破坏相邻分区。本方案把 A/B 边界定在 0x08040000（扇区6起点）和 0x080A0000（扇区9起点），完美对齐。

#### ② IROM1 的作用（Keil → Target → Memory）

IROM1 配置告诉**链接器**代码的存放起始地址和最大尺寸：
- **Start**：链接器把代码从该地址开始排放，所有符号地址据此计算。
- **Size**：代码区上限，超出则链接报错（防溢出到相邻分区）。

它**不影响 J-Link 烧录地址**——烧录地址由 FlashDriverDll 的 `-FS`（Flash Start）决定。所以 IROM1 和 FS 必须一致，否则"链接地址"和"烧录地址"错位，APP 跑飞。

#### ③ VECT_TAB_OFFSET（向量表偏移寄存器）

Cortex-M 上电后，`SCB->VTOR` 默认为 0，即中断向量表在 0x08000000（Bootloader 区）。APP 不在 0 位置，必须把 VTOR 指向自己的向量表：

```c
#define VECT_TAB_OFFSET  0x00040000  // A区：0x08040000 - 0x08000000
```

该宏在 `system_stm32f4xx.c` 的 `SystemInit()` 中生效：
```c
SCB->VTOR = FLASH_BASE_ADDRESS | VECT_TAB_OFFSET;
```

**若忘记设置**：APP 运行后一旦触发任何中断（SysTick/USART/EXTI），CPU 会去 0x08000000 找向量表，跳进 Bootloader 的中断函数，立即跑飞或 HardFault。

## 疑难三：A↔B 互跳卡死 / OLED 花屏（核心疑难）

### 3.1 现象

| 跳转路径 | 跳转前环境 | 结果 |
|----------|-----------|------|
| Bootloader → A | 裸机，只初始化 LED | ✅ 正常 |
| Bootloader → B | 裸机，只初始化 LED | ✅ 正常 |
| A → B | FreeRTOS + 大量外设运行中 | ❌ OLED 花屏、卡死 |
| B → A | FreeRTOS + 大量外设运行中 | ❌ 同上 |

### 3.2 根因分析

APP 间**直接跳转**时，`Jump_To_Partition()` 只清了 NVIC 和 SysTick，**没有关闭任何外设**，导致外设状态"悬在半空"：

1. **OLED 软件 IIC 总线死锁（花屏元凶）**：
   软件 IIC 用 GPIO 模拟。跳转瞬间 SDA 可能正被 OLED 从机拉低（ACK 应答中）。新 APP 启动后发 IIC 起始条件，检测到 SDA=0，误以为总线忙，时序全乱 → 花屏。

2. **FreeRTOS 任务调度未停止**：
   `KeyP4_LongPressedCallback` 里的 `delay_ms()` 期间，SysTick 中断仍触发任务切换。`app_task1` 的 `OLED_Display_Refresh` 正在刷 IIC 时，关中断跳转正好打断半字节传输。

3. **TIM/USART 外设残留**：
   TIM4(PWM)、TIM2(超声波) 跳转后仍在计数；USART2/3 的 RXNE 标志仍在，新 APP 使能中断后立即误触发。

### 3.3 解决方案：软复位法（工业界标准做法）

**核心思想**：不直接 APP→APP 跳转，而是 **APP → 软复位 → Bootloader → 目标 APP**。硬件复位会把所有外设/时钟/GPIO 清零，复用已验证可用的 Bootloader→APP 跳转能力。

#### 步骤一：APP 写标志 + 触发软复位

```c
// 在 key_task.c 的 KeyP4_LongPressedCallback 末尾
RCC_APB1PeriphClockCmd(RCC_APB1Periph_PWR, ENABLE);
PWR_BackupAccessCmd(ENABLE);                                    // 允许写备份域
RTC->BKP0R = (target == PARTITION_A_ADDR) ? JUMP_FLAG_TO_A      // 0xA5A50001
                                           : JUMP_FLAG_TO_B;     // 0xA5A50002
BLE_PRINTF("[KEY4] 触发软复位 -> 0x%08X\r\n", target);
delay_ms(50);                                                   // 等串口输出完
NVIC_SystemReset();                                             // 系统复位，不返回
```

#### 步骤二：Bootloader 读标志 + 跳转

```c
// 在 Bootloader main() 开头
RCC_APB1PeriphClockCmd(RCC_APB1Periph_PWR, ENABLE);
PWR_BackupAccessCmd(ENABLE);
uint32_t jump_req = RTC->BKP0R;
RTC->BKP0R = 0;                              // 清标志，防下次复位重复跳

if (jump_req == JUMP_FLAG_TO_A && Check_APP_Valid(APP_A_ADDRESS))
    Jump_To_Application(APP_A_ADDRESS);
else if (jump_req == JUMP_FLAG_TO_B && Check_APP_Valid(APP_B_ADDRESS))
    Jump_To_Application(APP_B_ADDRESS);
// 否则走默认逻辑（A 优先）
```

### 3.4 涉及知识点

#### ① NVIC_SystemReset() — 软件触发系统复位

```c
#define NVIC_SystemReset()  SCB->AIRCR = ((0x5FA << 16) | (SCB->AIRCR & 0x700) | (1<<2))
```

向 `SCB->AIRCR` 写入特定 key（0x5FA）并置 SYSRESETREQ 位，触发**系统级复位**。效果等同按 RESET 键：
- 所有外设寄存器恢复默认
- 所有时钟恢复默认（HSI）
- GPIO 复位为浮空输入
- NVIC、SysTick 清零
- **SRAM 内容保留**（但 C 启动代码会重新初始化 .bss/.data）
- **备份域（RTC 寄存器）保留** ← 这正是传递标志的关键

#### ② RTC 备份寄存器（BKP0R ~ BKP19R）

STM32F407 有 20 个 32 位备份寄存器，位于 RTC 模块内：

| 特性 | 说明 |
|------|------|
| 掉电保持 | 由 VBAT 供电，断电不丢（无电池则复位可能丢） |
| 软复位保持 | **系统复位不会清除**，是软复位传递标志的理想载体 |
| 写保护 | 需先 `PWR_BackupAccessCmd(ENABLE)` 置 DBP 位才能写 |
| 读保护 | 直接读 `RTC->BKP0R` 即可，无需解锁 |

**为什么选 BKP 而不是普通 SRAM？** 软复位后 SRAM 内容虽在，但 C 启动代码的 `__main` 会重新初始化 .bss 段（清零），可能把标志清掉。备份寄存器独立于 SRAM，启动代码不碰它，绝对安全。

#### ③ 软复位 vs 直接跳转的对比

| 对比项 | 直接跳转 Jump_To_Partition | 软复位法 |
|--------|---------------------------|---------|
| 外设状态 | 残留（脏） | 全部复位（干净） |
| GPIO 状态 | 残留 | 复位为浮空输入 |
| IIC 总线 | 可能死锁 | 释放 |
| FreeRTOS 状态 | 残留 | 彻底销毁 |
| 跳转耗时 | 快（μs 级） | 慢（几十 ms，含 Bootloader 初始化） |
| 可靠性 | 低（易漏关外设） | 高（硬件保证） |
| 适用场景 | Bootloader→APP（裸机环境干净） | APP→APP（环境脏） |

#### ④ 为什么 Bootloader→APP 直接跳转能成功

Bootloader 是裸机程序，`main()` 里只初始化了 LED 的 GPIO，没开任何中断、没跑 FreeRTOS、没用 IIC/USART/TIM。跳转前环境本就"干净"，所以直接跳转没问题。这也是软复位法复用 Bootloader 跳转能力的理论依据。

## 疑难四：UTF-8 编码导致编译错误

### 4.1 现象

编辑代码后编译报三个错误：

```
error: #8: missing closing quote
                 OLED_ShowString(0,3,(u8 *)"銆傘€傘€?,20);

error: #165: too few arguments in function call
                 RCC_APB1PeriphClockCmd(RCC_APB1Periph_PWR, ENABLE);

error: #18: expected a ")"
                 RCC_APB1PeriphClockCmd(RCC_APB1Periph_PWR, ENABLE);
```

### 4.2 根因

`RCC_APB1PeriphClockCmd` 那两行错误是**假的**——是第一个错误的**级联**：

```
文件被编辑工具存成 UTF-8（原应 GBK）
        │
        ▼
Keil 按 GBK 读取 → 全角句号"。"乱码 → 字符串引号未闭合 (error #8)
        │
        ▼
编译器把后续所有代码当成字符串内容 → RCC_APB1PeriphClockCmd 被解析错 (error #165/#18)
```

全角句号"。"的编码差异：

| 编码 | 字节序列 |
|------|----------|
| GBK | A1 A3（2 字节） |
| UTF-8 | E3 80 82（3 字节） |

当 UTF-8 的 `E3 80 82` 被 Keil 当 GBK 解读时，这几个字节与后续字符组合，恰好"吞掉"了字符串的闭合引号 `"`。

### 4.3 解决方案

用 PowerShell 检测并转换编码：严格 UTF-8 解码成功的文件即为 UTF-8，转回 GBK（CodePage 936）：

```powershell
$utf8Strict = New-Object System.Text.UTF8Encoding $false, $true  # 第2参数true=严格模式
$gbk = [System.Text.Encoding]::GetEncoding(936)

$bytes = [System.IO.File]::ReadAllBytes($path)
try {
    $str = $utf8Strict.GetString($bytes)   # GBK文件会抛异常
    # 是UTF-8 → 转GBK
    [System.IO.File]::WriteAllBytes($path, $gbk.GetBytes($str))
} catch {
    # 是GBK → 不动
}
```

### 4.4 涉及知识点

#### ① GBK vs UTF-8 编码

| 编码 | 中文名 | 字节长度 | 特点 |
|------|--------|----------|------|
| GBK | 汉字内码扩展规范 | 中文 2 字节 | 中文 Windows 系统默认编码（CodePage 936） |
| UTF-8 | Unicode 变长编码 | 中文 3 字节 | 国际通用，Web/Linux 默认 |

中文版 Windows + Keil 的 ARMCC 编译器默认按 **GBK** 读取源文件。若文件实为 UTF-8，中文部分被按 GBK 解码就乱码。

#### ② 级联编译错误

编译器是流式解析的。当某处字符串引号未闭合，词法分析器会把后续所有字符（包括换行）都当成字符串内容，直到遇到下一个 `"`。这导致：
- 后面几十行代码全部"消失"进字符串
- 本来正确的代码报"参数太少""缺少括号"等离谱错误

**排查技巧**：遇到一连串莫名其妙的错误，**先看第一个错误**（通常是 missing closing quote / unterminated string），修好它，后面的级联错误往往自动消失。

#### ③ 严格 UTF-8 检测原理

`UTF8Encoding(false, true)` 第二参数 `throwOnInvalidBytes=true` 开启严格模式：遇到非法 UTF-8 字节序列会抛异常。

- UTF-8 文件：严格解码成功 → 判定为 UTF-8
- GBK 文件：GBK 的双字节中文（如 A1A3）通常不是合法 UTF-8 序列 → 抛异常 → 判定为 GBK

这是个可靠的编码判别法。

## 知识点串联：一次完整的 OTA 分区切换

以"A 区运行中，长按 KEY4 切换到 B 区"为例，串联所有知识点：

```
[A 区运行] FreeRTOS + OLED + 蓝牙 + WiFi
     │
     │ 长按 KEY4 3秒
     ▼
[写标志] RTC->BKP0R = 0xA5A50002    ← 疑难四的备份寄存器知识点
     │
     ▼
[NVIC_SystemReset()]                ← 疑难三的软复位知识点
     │
     │ 硬件复位：外设/GPIO/时钟全清零，BKP 保留
     ▼
[Bootloader main()]
     │
     │ 读 BKP0R = 0xA5A50002，清零
     ▼
[Check_APP_Valid(0x080A0000)]       ← 疑难一的有效性检查知识点
     │ 检查 SP∈SRAM1/SRAM2 + Reset_Handler∈Flash + Thumb位
     ▼
[Jump_To_Application(0x080A0000)]   ← 裸机环境干净，直接跳转
     │ 设 SCB->VTOR = 0x080A0000    ← 疑难二的向量表偏移知识点
     │ 设 MSP = B区栈顶
     ▼
[B 区 SystemInit()] VECT_TAB_OFFSET=0x000A0000 生效
     │
     ▼
[B 区 main()] 正常运行，OLED 不花屏
```

---

## 经验总结

1. **APP 有效性检查要全面**：SRAM1+SRAM2 都要认，Reset_Handler 范围 + Thumb 位都要查。
2. **分区边界对齐扇区**：擦除以扇区为单位，边界错位会破坏相邻分区。
3. **三个配置必须一致**：IROM1 Start、FlashDriverDll FS、VECT_TAB_OFFSET 三者指向同一地址。
4. **APP 间跳转用软复位**：直接跳转外设残留必出问题，软复位借道 Bootloader 最可靠。
5. **标志传递用备份寄存器**：软复位不清 BKP，是跨复位传标志的标准载体。
6. **中文源文件用 GBK**：Keil 中文环境按 GBK 读，编辑后务必转回 GBK。
7. **级联错误看第一个**：一连串离谱错误，修好第一个后面的自动消失。
